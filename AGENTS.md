# AGENTS.md

This file provides guidance to agents when working with code in this repository.

Keep repository guidance here and user instructions in `README.md` up to date with code and workflow changes. `CLAUDE.md` imports this file with `@AGENTS.md`. No additional agent tooling or memory files are required.

## Project Overview
- `img_tagger.py` — single-file CLI: tags JPEG/WebP/PNG/GIF files via a vision-language model on a local or LAN server (Ollama or LM Studio), writing tags into image metadata. `--clear` strips tags/metadata back out instead (used to reset images for testing; no model backend needed).
- `prompt.txt` — externalized LLM prompt; takes precedence over the `DEFAULT_PROMPT` fallback hardcoded in `img_tagger.py`.
- Flat repo layout: no package structure, not installable (`pyproject.toml` only holds Ruff and coverage config; no `setup.py`). Tests live in `tests/` (pytest, configured by `pytest.ini`). CI: GitHub Actions (see CI section).
- **Git workflow**: commits are allowed; prefer working on a branch and opening a pull request rather than pushing directly to `main`.
- Requires **Python 3.13+**.

## Build/Lint/Test Commands
Ruff (lint + format) is configured in `pyproject.toml`; CI fails on any Ruff finding or unformatted file. SonarQube Cloud (project `juusolatva_img_tagger`) runs in CI; keep functions under its cognitive-complexity limit of 15 by extracting `_private` helpers.
- Dependencies: `python3 -m pip install -r requirements.txt`; dev deps (pytest, pytest-cov, Ruff): `python3 -m pip install -r requirements-dev.txt`. Both backend clients are imported at module load, so install all runtime dependencies even for `--clear`; clearing needs no running model server.
- Lint/format: `ruff check .` and `ruff format .` (CI runs `ruff format --check`). Use the Ruff version pinned in `requirements-dev.txt`.
- Run tests: `python3 -m pytest` (offline: images generated on the fly, model backends faked). With coverage like CI: `python3 -m pytest --cov`
- Integration tests (opt-in, need a live backend + images in git-ignored `test_images/`; copies images to a temp dir, prints tags for manual quality review): `python3 -m pytest -m integration --run-integration -s [--tagger-backend lm-studio] [--tagger-host URL] [--tagger-model M] [--images-dir DIR]`. `--tagger-model` defaults to Ollama's `qwen3-vl:8b`, so with LM Studio also pass its model id. The `client` fixture uses `_create_client()`, so runs get `DEFAULT_TIMEOUT` and LM Studio's `max_retries=0`.
- Run tagger (Ollama, default): `python3 img_tagger.py <directory>`
- Run tagger (LM Studio): `python3 img_tagger.py <directory> --backend lm-studio --model qwen/qwen3-vl-8b` (LM Studio's own model id; see Backends)
- Recursive, custom model/workers: `python3 img_tagger.py <directory> -r --model <model> --workers 4`
- Clear all tags: `python3 img_tagger.py <directory> --clear [-r] [--workers N]`
- Help: `python3 img_tagger.py -h`
- Request timeout (seconds, default 600): `python3 img_tagger.py <directory> --timeout 1200`
- Model image size (megapixels, default 1): `python3 img_tagger.py <directory> --max-pixels 2`; `--max-pixels 0` sends original bytes (see Backends).
- Logging: `python3 img_tagger.py <dir> --log output.log` (see Logging under Core Rules)
- Note: commands use `python3` (Linux/macOS); on Windows use `python` (`python3` there is often the Microsoft Store alias).

## CI
`.github/workflows/ci.yml` (GitHub Actions) runs on pushes to `main`, pull requests and manual dispatch:
- **Ruff**: `ruff check` and `ruff format --check --diff`. `ruff-action` reads the Ruff version from the `ruff==` pin in `requirements-dev.txt`.
- **Tests**: `pytest --cov --cov-report=xml` on Ubuntu with Python 3.13 and 3.14, plus `windows-latest` with 3.14 (`fail-fast: false`; job names `Tests (<os>, Python <version>)`). Integration tests are skipped (no backend). Installs from `requirements-dev.lock` with `--require-hashes --only-binary :all:`, so every locked package needs a wheel for every matrix version and OS (Linux and Windows). The 3.14 jobs upload `coverage.xml` as the artifacts `coverage` (Linux) and `coverage-windows`; Sonar reads both (`sonar.python.coverage.reportPaths`), so the Windows-only file-safety branches count as covered.
- **SonarQube Cloud**: runs after the tests and scans with the downloaded Linux `coverage.xml` and `coverage-windows/coverage.xml` reports. Settings are in `sonar-project.properties` (sources `.`, `tests/**` excluded and treated as tests, `sonar.python.version` 3.13–3.14). Needs `SONAR_TOKEN` as both an Actions secret and a Dependabot secret (Dependabot-triggered runs read only Dependabot secrets). `if:` can't read secrets, so the job maps it to a job-level env var and the checkout, both coverage downloads and the scan step run only when that is non-empty; otherwise only a warning annotation explaining the skip runs. Fork PRs get no secrets, hence no scan and no SonarQube quality-gate status: don't make that status a required check. Coverage is configured in `[tool.coverage.run]` in `pyproject.toml` (branch coverage, `tests/` omitted, `relative_files = true` so Sonar can map the paths in `coverage.xml` to its sources, `patch = ["subprocess"]` so the `test_cli.py` subprocess runs count toward `setup_logging()` and the end-to-end paths). With that patch, tqdm's multiprocessing lock starts a `resource_tracker` child that outlives pytest-cov's combine and leaves an empty `.coverage.<host>.pid…` file (git-ignored, harmless).
- Every job in `ci.yml` has a `timeout-minutes`, and checkouts use `persist-credentials: false` (no job pushes).
- **OSV-Scanner** (`.github/workflows/osv-scanner.yml`): calls `google/osv-scanner-action`'s reusable workflows — full scan (`osv-scanner-reusable.yml`) on pushes to `main`, weekly schedule and manual dispatch, and PR diff scan (`osv-scanner-reusable-pr.yml`) on pull requests and `merge_group` (with `upload-sarif` disabled on fork PRs, which lack `security-events: write`). Both pass `--lockfile=requirements.txt:requirements-dev.lock`, `--no-resolve` and `-r ./` so the `.lock` file is scanned as a pip requirements lockfile and `requirements*.txt` minimum bounds are checked without resolving transitive dependencies from PyPI.
- All actions, including GitHub's own `actions/*` and reusable workflows, are pinned to full 40-character commit SHAs with a `# vX.Y.Z` comment.
- **Dependabot** (`.github/dependabot.yml` holds schedule, grouping and cooldown): updates GitHub Actions (SHA pins together with their `# vX.Y.Z` comment) and Python packages (grouped minor/patch, one PR per major). Its pip updater reads only `*.txt`/`*.in` files, so it bumps the bounds in `requirements*.txt` and the `ruff==` pin but never regenerates `requirements-dev.lock`. The `lock` job in `ci.yml` (`Lockfile`) recompiles the lock with the pinned `uv` and fails on any diff, so a Dependabot PR stays red until you regenerate the lock (below) and push it to the PR branch. Keep the `uv==` pin in `ci.yml` in step with what you use locally.
- **`requirements-dev.lock`**: hash-locked, cross-platform lock of `requirements-dev.txt` (and thus `requirements.txt`) for Python ≥3.13. Only CI installs it; end users still get the `>=` bounds. After changing either requirements file, regenerate it with `uv pip compile requirements-dev.txt --universal --python-version 3.13 --generate-hashes --no-header -o requirements-dev.lock`. That keeps the existing pins where they still fit; to bump versions add `--upgrade` (all) or `-P <package>` (one).
- Changing the supported Python range means updating the CI matrix, `sonar.python.version`, Ruff `target-version`, the lock's `--python-version` and the static Python badge in `README.md` together.

## Backends
- `--backend ollama` (default): `ollama` Python client, default host `http://localhost:11434`. `get_tags_ollama()` passes guarded image *bytes* in `images`; the client base64-encodes the snapshot without reopening its path, so a remote Ollama needs no shared filesystem.
- `--backend lm-studio`: `openai` client against LM Studio's OpenAI-compatible API, default host `http://localhost:1234`. `get_tags_lm_studio()` sends the prepared image bytes as a base64 data URL whose MIME type matches the generated PNG/JPEG encoding. Original-byte sends use the Pillow-detected format (fallback `image/jpeg`), not the extension. `api_key="lm-studio"` is a required placeholder string, not a real credential.
- **What the model gets**: `_model_image()` builds a copy from the guarded snapshot: first frame only, `ImageOps.exif_transpose()`, scaled down (LANCZOS, never up, aspect kept) to at most `--max-pixels` megapixels (default `DEFAULT_MAX_MEGAPIXELS` = 1.0; JPEG sources are first decoded with `draft()` at a reduced scale), re-encoded without any metadata (`frame.info` is emptied after `convert()`: Pillow carries `info` through conversion/resizing and its encoders write back a JPEG `comment` and a PNG `icc_profile`; security audit finding 2) as PNG (PNG/GIF sources or transparency) or JPEG quality `MODEL_JPEG_QUALITY` (90); 16-bit PNGs are mapped to 8-bit first. LM Studio's data-URL MIME type comes from that encoding. `--max-pixels 0` sends the original bytes unchanged with the Pillow-detected MIME type (fallback `image/jpeg`), and so does any image the copy can't be made from (any `Exception`: Pillow also raises `struct.error`, `zlib.error`, `TypeError` etc. outside `OSError`; e.g. a truncated JPEG: `verify()` in `get_image_format()` doesn't decode JPEG pixel data, while servers decode leniently); that fallback is only logged and includes any original metadata. Image preparation changes only the outgoing copy; tagging still edits metadata on disk. Why 1 MP (measured 2026-10, Qwen3-VL 4B on both backends): Ollama enlarges smaller images to ~1,200 prompt tokens, so less saves nothing there (LM Studio has no such floor); small diagram labels were still read at 1 MP but not at 0.5 MP; a 12 MP photo took 29 s vs 5 s at 1 MP with equivalent tags. `--max-pixels` must be >= 0 and finite (`math.isfinite()` in `_argument_error()` rejects `nan` and `inf`).
- **`--model`**: one default for both backends, `qwen3-vl:8b`, which is Ollama naming. LM Studio ids differ (e.g. `qwen/qwen3-vl-8b`; list them at `<host>/v1/models`), so with LM Studio `--model` must always be passed.
- **LM Studio vision setup** (found by testing, not visible in code): a GGUF model only counts as vision-capable (`type: "vlm"` in `<host>/api/v0/models`) once its vision projector `mmproj-*.gguf` is downloaded; otherwise every image fails with HTTP 400 `... does not support image inputs`. LM Studio loads the model on the first request, so the first image is slower.
- **`--host`**: no argparse default; `process_directory(host=None)` fills in the backend's localhost URL from `DEFAULT_HOSTS` (also for imported callers), so the ollama client never falls back to `OLLAMA_HOST`. The ollama client normalizes hosts (`192.168.1.10` → `http://192.168.1.10:11434`); LM Studio uses `f"{host.rstrip('/')}/v1"`, so pass `http://host:port` without `/v1` (a trailing slash is fine). Servers on another LAN machine work.
- **Client hardening** (`_create_client()`, security audit findings 1 and 3, review finding 1): both SDKs follow redirects by default, which would let the selected server forward the image and prompt to any host this machine can reach, so both are built with `follow_redirects=False` (Ollama: client kwarg; LM Studio: `http_client=DefaultHttpxClient(follow_redirects=False)`); a redirect fails the request (`ResponseError`/`APIStatusError: Error code: 307`). The ollama client adds `OLLAMA_API_KEY` as a bearer token to every host (and an empty `Authorization` header still triggers that fallback), so an httpx callable `auth=_without_authorization` pops the header per request. The openai client fills `OpenAI-Organization`/`OpenAI-Project` from `OPENAI_ORG_ID`/`OPENAI_PROJECT_ID`; `default_headers` with `Omit()` removes them (`api_key="lm-studio"` already keeps `OPENAI_API_KEY` out). `trust_env` stays on (proxy settings and `NO_PROXY` keep working). `TestClientHardening` in `test_backends.py` checks the real clients against a local redirecting server. Clients are closed after use (`contextlib.closing` in `_check_server()`, `client.close()` in `process_directory()`'s `finally`), so test fakes need a `close()`. An empty `choices` list from LM Studio counts as an empty reply.
- **Server check**: before any image, `process_directory()` calls `_check_server()`, which lists the models (`client.list()` for Ollama, `client.models.list()` for LM Studio) with its own client and timeout `min(--timeout, SERVER_CHECK_TIMEOUT)` (10s), so an unreachable LAN host fails in seconds instead of after `--timeout`. Any exception, or a model that isn't listed, raises `_ServerCheckError` (message lists the available models, plus an `ollama pull` or LM Studio-id hint); `main()` prints `Error: …` and returns 1. Matching (`_model_matches()`): exact name; Ollama also accepts an untagged name for `<name>:latest`; LM Studio also accepts `<id>@<quant>`. It runs after `_load_prompt()` (local failures first) and not for `--clear`. It deliberately runs before any skip check, so a fully tagged folder also exits 1 when the server is down (accepted in PR #25 review: a tagging run needs the server; checking lazily would need an abort path through the worker pool). The check doesn't test vision support. Test fakes list `conftest.FAKE_MODELS`; `test_cli.py` subprocess tests use the `failing_ollama` stub server (lists the default model, fails every chat) to reach per-image failures.
- **Request timeout**: `--timeout` (default `DEFAULT_TIMEOUT` = 600s, must be > 0 and finite: `math.isfinite()` rejects `nan`, which `nan <= 0` would let through, and `inf`, on which the HTTP clients' sockets raise `OverflowError`) is passed to both clients by `_create_client()`. It must cover the whole non-streamed reply, including model loading. A timeout raises in the worker and marks that image `FAILED`. The LM Studio client uses `max_retries=0`: the openai default (2) would resend a timed-out request to a server still busy with it.

## Core Rules & Architecture
- **CLI**: `main(argv=None) -> int` parses (`_build_parser()`), checks `_log_path_error()` and `_argument_error()`, only then opens the log with `setup_logging()` (so invalid arguments create no log file or folders), and calls `process_directory()`. Invalid arguments, log-open failures, a `_ServerCheckError` and any `OSError` from `process_directory()` (the folder itself: an `_UnsafeImagePath` from `_find_images()`, e.g. group-writable, a symlinked part via `_open_folder()` or a `..` after the first part, or a folder it can't list) → print `Error: …`, return 1; `__main__` is only `sys.exit(main())`. Argument handling is tested in-process (`TestMain` in `test_cli.py`); subprocess tests cover logging and console encoding. Defaults live in `DEFAULT_MODEL`, `DEFAULT_HOSTS`, `DEFAULT_TIMEOUT` and `DEFAULT_MAX_MEGAPIXELS`.
- **Pipeline**: `process_directory()` → `_find_images()` (extension filter `IMAGE_EXTENSIONS`, `iterdir()`/`rglob("*")`; the root is first opened with `os.scandir()`, because `rglob()` silently yields nothing for a folder it can't list; opening is enough, and `iterdir()` would read every entry) → `_load_prompt()` → `_check_server()` → `_create_client()` → quit listener → `_run_tasks()` (`ThreadPoolExecutor` + `as_completed` + tqdm; each `process_single_image()` result `(status, name, message, duration)` goes to `_RunStats.record()`) → `_print_report()` (`Processed images` counts only images tagged during the current run). Per image: one guarded read `_read_image_snapshot()` (bytes plus the source `stat`; an `OSError` such as an unsafe folder → `FAILED` with `Could not read image: <reason>`) whose bytes serve every later step → `get_image_format(data)` (Pillow verify; invalid → `FAILED`; a format outside `TAGGABLE_FORMATS`, e.g. BMP or MPO, → `FAILED` before any model call) → `is_already_processed()` (`SKIPPED`) → stop check (`CANCELLED`) → backend call (`data=` snapshot) → `parse_model_output()` → `tag_image(expected=snapshot)`, whose `_image_edit()` refuses a file that `_same_version()` (same identity, size and `st_mtime_ns`) says was replaced or modified since the snapshot (`File changed during processing`), so tags never describe other content. Two reads per tagged image: the snapshot and the edit. An exception escaping `process_single_image()` is counted and listed in the report (`failed_log`) by `_run_tasks()`.
- **Format dispatch**: `tag_image()`, `is_already_processed()` and `clear_tags()` all route on the Pillow-detected format, not the extension (a PNG named `.gif` is tagged, detected and cleared via pyexiv2). The extension decides only when Pillow can't read the file (`_is_gif()`).
- **Worker limit**: Max 4 concurrent workers (matches both backends' default concurrency limits). Default is 1. Enforced in CLI argument validation (`_argument_error()`: `1 <= workers <= 4`), not inside `process_directory()` itself.
- **Skip marker**: Files with `[PROCESSED BY AI]` are skipped automatically (`is_already_processed()`) without validating the stored tags or their origin. JPEG/WebP/PNG: any EXIF or XMP value (`_pyexiv2_has_marker()`); if pyexiv2 finds none or fails, any string in Pillow's `img.info` (`_pillow_has_marker()`, e.g. PNG text chunks). GIF: the comment only. Unreadable metadata → `_warn()` and treated as not tagged.
- **Prompt source**: `prompt.txt` in the script directory takes precedence over the in-code `DEFAULT_PROMPT` fallback. If `prompt.txt` exists but cannot be read, or is empty after stripping, execution aborts (`sys.exit(1)`). `DEFAULT_PROMPT` is implicitly concatenated string literals: keep the trailing space on each piece.
- **Tag count & normalization**: Output is normalized via `normalize_tags()` (strip whitespace, lowercase, order-preserving deduplication, capped at 12 tags, tags longer than `MAX_TAG_LENGTH` (64) dropped: such an entry is a sentence, e.g. a refusal or explanation that the comma fallback split up). Nothing else is rewritten or filtered: underscores stay (Qwen sometimes replies `digital_art`), and so do non-English tags (Qwen models occasionally emit a Chinese tag despite the English-only prompt). Deliberately unfiltered: `prompt.txt` may ask for tags in any language. Fewer than 6 valid tags after parsing marks that image as `FAILED`.
- **Tag parsing**: `parse_model_output()` returns `None` for `None`/empty content (the backends also turn a `None` reply into `""`, e.g. a reasoning model cut off by `max_tokens`), then drops everything up to the last `</think>` (reasoning from thinking models; a `<think>` without any `</think>` returns `None`, since cut-off reasoning has no answer and its prose would otherwise pass the comma fallback), removes Markdown code-fence lines (```` ``` ```` / ```` ```json ````, also with CRLF line endings), returns `None` for a reply that opens with an English refusal (`_REFUSAL`, anchored at the start with only whitespace or Markdown emphasis before it: `I'm sorry`, `I can't`/`cannot`/`won't`, `I am unable`, `Sorry, (but) I`, `Unfortunately, I`, `As an AI`, `I apologize`, `My apologies`; a tag list merely containing `sorry` or `i can't even` is unaffected, and so is a JSON or bullet list whose first tag is such text, since `["` and `- ` aren't skipped (PR #31 Greptile review); refusals in other languages aren't recognized), then tries several patterns in order:
  1. JSON array (`json.loads` on full string or bracketed `[...]` substring; strings and numbers are kept, booleans dropped).
  2. Bullet points at line start (`[-•★●]`, or Markdown `*` followed by a space so a bold `**Tags:**` line isn't one; minimum 6 items expected; splits each line on commas and strips `"`/`'`). Hyphens inside tags (`tag-1`) are not bullets.
  3. Numbered lists (`\d+\.`, minimum 6 items expected; splits each line on commas and strips `"`/`'`).
  4. Intro text: `tags`/`keywords` within the first ~40 chars, followed by a colon later on the same line (`Here are the tags for this image:`) or a dash right after (`Keywords -`). Parsed via `parse_text_tags()`, which drops common English stop words but keeps short tags like `3d`/`ui`.
  5. Comma- and/or newline-separated list fallback.

  A JSON list containing strings (`_json_list()`: the whole reply, else its first-to-last bracketed segment) is authoritative: fewer than 6 tags → `None`, because splitting the JSON text on commas would turn `[true`/`d]` into tags. Only a JSON list without strings (e.g. an incidental `[1]` in prose) falls through. A matched bullet/numbered/intro pattern likewise returns its result (or `None` → `FAILED`) without trying later patterns.
- **Concurrency & Locks**: Images are processed in parallel via `ThreadPoolExecutor`. `pyexiv2` is not thread-safe: all `pyexiv2` reads (`_pyexiv2_has_marker()`), writes (`write_metadata()`) and clears (`_clear_standard()`) are serialized through `metadata_lock = threading.Lock()`. Both `write_metadata()` and `_clear_standard()` hold it only around pyexiv2 calls, not during the Pillow auto-heal re-save, so a slow re-encode doesn't stall the other workers. Replacement occurs after releasing the metadata lock. Model API calls, the GIF block editing and Pillow operations (format verification, the skip-check fallback, the auto-heal re-save) are intentionally outside the lock to preserve concurrency.
- **Logging**: The `img_tagger` logger has a `NullHandler`, so without `--log` nothing is logged (no stray stderr warnings or tracebacks over the progress bar). The console shows results via `tqdm.write()`/`print()`. Problems the user must see either way go through `_warn()`, which both logs a warning and prints `  Warning: …` via `tqdm.write()`. These are pyexiv2/Pillow metadata read failures in `is_already_processed()`, the auto-heal re-save in `write_metadata()` and failure to preserve the owning group in `_restore_group()`. `--log` (`setup_logging()`) appends to the file with our logger at `DEBUG` and other libraries at `INFO` (a filter on our handler; the root level is raised to `INFO` if needed but never lowered from a more verbose level an embedding application set), through a `_LogHandler` added to the root logger (not `basicConfig()`, which silently ignores new handlers, leaking the open file, when the root already has one, e.g. pytest's; a second call replaces and closes our earlier handler; closing it closes the file), which keeps httpx request lines and drops Pillow's per-chunk noise. The log records run settings, the prompt, each image's outcome and duration, raw model replies (cut to `MAX_LOGGED_REPLY_CHARS` = 4000 by `_log_excerpt()`, so a runaway reply can't fill the disk), tracebacks and a final summary. `_LogFormatter` escapes control characters in every message with `_shown()`, so a file name or reply containing newlines can't fake extra records (tracebacks are appended unescaped; audit finding 13). Because raw replies can be steered by text inside an image, `main()` first checks the path with `_log_path_error()`: it must end in `.log` (case-insensitive) and, if it exists, be a regular file and not a symlink; otherwise exit 1 before anything is created. This keeps a misused `--log` (e.g. a prompt-injected agent) from appending to shell profiles, keys or source files. The path is deliberately not confined to the current directory (`--log /tmp/run.log` stays valid). `_log_path_error()` is only the early, friendly check: `setup_logging()` then opens the file exactly once with `_open_log()` (POSIX `O_NOFOLLOW | O_APPEND | O_CREAT | O_NONBLOCK`, new files mode `0o600` since the log holds raw replies and paths, Windows `CreateFileW` with `FILE_APPEND_DATA | READ_CONTROL` and `FILE_FLAG_OPEN_REPARSE_POINT`, a new file created with the protected owner-only DACL `_Win.PRIVATE_SDDL` = `D:P(A;;FA;;;OW)` from `_windows_private_security()` instead of the folder's inherited one; audit finding 9), requires a regular file owned by the current user (`_owned_by_current_user()`: POSIX uid; Windows `_windows_owned_by_me()` compares the owner SID with the token's user and default-owner SIDs, since an elevated administrator's files may belong to Administrators; a file planted in `/tmp` or a shared folder by someone else is refused). An existing Windows log keeps its DACL: only its owner is checked, like POSIX checks the uid and not the mode, and logs to that stream through a `StreamHandler`, written with `errors="backslashreplace"` like logging's own `FileHandler` (non-UTF-8 POSIX file names arrive as lone surrogates and would otherwise make every record about them fail). So swapping the leaf for a symlink after the check can't redirect the appends (security review finding 2). An open failure makes `main()` print `Error: Could not open the log file …` and return 1. Ancestor folders are resolved normally (macOS `/tmp` is a symlink).
- **Console output integrity**: names and messages from files or servers go through `_shown()` before printing (`_RunStats.record()`, so also the report's failure list, `_run_tasks()`'s unexpected errors, `clear_tags()` and `_warn()`): C0/C1 control characters and bidirectional overrides become escapes (`\n`, `\x1b`, `\u202e`), other Unicode is kept. Successful tags print as a Python list, already escaped.
- **Console encoding**: `main()` reconfigures `sys.stdout` with `errors="replace"`. Redirected output on Windows uses the ANSI code page (e.g. cp1252), which can't encode the `[✓]` success prefix or many file names; without this every success was counted as a failure and a non-ASCII name aborted the run. Tests that call functions directly don't get it (`test_cli.py` covers it via a subprocess with `PYTHONIOENCODING=ascii`).
- **Graceful quit**: Press `Q` during execution to trigger graceful shutdown. Monitored by a daemon thread (`listen_for_quit()`): `_wait_for_quit_windows()` (`msvcrt`) on Windows, which discards the scan code after an extended-key prefix (`\x00`/`\xe0`; Page Down is `\xe0` `Q`); on POSIX `_cbreak_stdin()` + `_wait_for_quit_posix()` (`termios`/`tty`/`select`, EOF detection; plain reads with `idle_sleep=0.1` when stdin isn't a tty; with no usable stdin at all, e.g. `None`, closed or a `StringIO`, the fallback's `OSError`/`ValueError`/`AttributeError` is logged at debug and the listener returns). The POSIX loop reads the raw fd with `os.read()`, not `sys.stdin.read()`, so Python's buffer can't hide pending keys from `select()`. In-flight requests finish (or hit `--timeout`). Queued tasks return `CANCELLED` first thing in `process_single_image()`, before the file is read (so a large batch stops promptly; already tagged or invalid queued images are cancelled too, not skipped or failed), which is neither printed nor counted. `process_directory()` sets `stop_event` in its `finally` after every run, so the listener exits (restoring the POSIX terminal) instead of being waited out by `join(timeout=2)`.

## Metadata Schema
- **JPEG / WebP / PNG**:
  - EXIF: `Exif.Photo.UserComment` contains `"<tag1>, <tag2>, ... [PROCESSED BY AI]"`.
  - XMP: `Xmp.dc.subject` contains the raw tag list (`['tag1', 'tag2', ...]`); `Xmp.dc.description` contains `"Tags: <tag1>, <tag2>, ... | [PROCESSED BY AI]"`.
  - Only these three fields are replaced; other EXIF/XMP/IPTC survives tagging (unless auto-heal runs).
- **GIF**: Comment field only (no EXIF/XMP support). Stored as `"<tag1>, <tag2>, ... [PROCESSED BY AI]"`, replacing any existing comment.
- **Metadata Clearing (`--clear`)**: `process_directory(clear=True)` delegates to `clear_directory()` → `clear_tags()` per file (`_clear_standard()` / `_clear_gif()`); no prompt/client/quit listener/report. `clear_tags()` validates a guarded snapshot first and then edits with `_image_edit(expected=snapshot)` (two reads, like tagging), so files that `get_image_format()` can't read (`Unreadable image`, unless the extension is `.gif`; a non-GIF `.gif` then fails with `Not a GIF file`) or detects outside `TAGGABLE_FORMATS` (`Unsupported file format: <fmt>`, e.g. BMP or MPO) are refused unchanged without a temporary. Per-file failures are printed and logged, not raised. Strips EXIF, XMP, and IPTC (`_clear_all()`, including unrelated metadata) for standard images, and removes every comment block from GIFs (`_set_gif_comment(source, "")`; nothing else changes, so a GIF without comments is rewritten byte for byte). XMP needs `clear_xmp()` *and* `modify_raw_xmp("")`: on WebP, `clear_xmp()` alone leaves the XMP chunk in the saved file. `clear_comment()` is never called, so JPEG `COM` and PNG `Description` comments (and other PNG text chunks) survive; a marker in a preserved PNG text chunk still causes a skip afterwards.

## File Replacement & Atomic Safety
- **Temp file placement**: Temporary files MUST always be created in the target image's directory (POSIX exclusive `os.open(..., dir_fd=parent_fd)`; Windows `_create_windows_temp()`, `CreateFileW` with `CREATE_NEW`). Both use random `tmp<hex>.tmp` names. This ensures replacements remain atomic on the same filesystem/mount point without cross-device link errors.
- **pyexiv2 never gets a path**: `_modify_with_pyexiv2()` reads the retained temporary file object into `pyexiv2.ImageData`, applies the edit and writes `get_bytes()` back with Python; `_pyexiv2_has_marker()` reads via `ImageData` too. On Windows pyexiv2 can't open paths with non-ASCII characters in the file name *or any folder* (`encoding="utf-8"` fails; `"mbcs"` covers only the ANSI code page), and the temp file sits in the image's folder. Never pass a path to `pyexiv2.Image`. (`ImageData` holds the whole file in memory and refuses files ≥2 GB.)
- **Source reads**: `_read_image_bytes()` uses `_image_parent()` and `_source_bytes()`; all Pillow reads use private byte snapshots, and both backends receive guarded bytes. Direct backend/writer entry points use these helpers too. Discovery (`_find_images()`) returns an ordered `dict` of path → `lstat` for regular files only (leaf symlinks excluded); `process_single_image(found=)` and `clear_tags(found=)` pass it down, and `_source_bytes()` refuses a file at that path whose identity (`samestat`) differs (`File changed since it was found`): someone allowed to rename folders above a collection could otherwise swap in a different collection between discovery and the read (audit finding 4). Read-time checks also reject symlinked ancestors and nonregular inputs. `_source_bytes()` refuses files over `MAX_IMAGE_BYTES` (256 MiB, `EFBIG` `Image is larger than 256 MiB`), checked on `st_size` and again by reading at most one byte more, so a file growing meanwhile stays bounded (audit finding 10); POSIX reads switch the descriptor back to blocking (`O_NONBLOCK` only refuses FIFOs at open). POSIX opens parents/leaf with `O_NOFOLLOW` and pins directory descriptors. The final image directory must belong to root or the current UID and may not be group/other writable. Ancestors are pinned, not trusted by their reported owner; this avoids trusting unmapped/overflow UIDs in user namespaces. Same-UID/root mutation is outside this boundary. Paths containing `..` are refused by `_image_parent()`; only `_find_images()` first resolves *leading* `..` parts against `os.getcwd()` (`_without_leading_parent_refs()`; POSIX `getcwd()` has no links and Windows resolves `..` by name, so this is the folder the shell meant), so `../memes` works while `a/../b`, where `a` could be a link, stays refused. `_check_directory()` names the refused folder and also rejects group-writable folders of a user-private group (umask 0002 makes `mkdir` folders 775); it can't tell those from shared groups, so they stay refused with a `chmod go-w` hint. Windows (`parent_fd` is `None` there) pins every ancestor with `_pin_windows_directory()`: a `CreateFileW` handle with `FILE_TRAVERSE` (else `FILE_LIST_DIRECTORY`; a folder granting neither, reachable only via the bypass-traverse privilege, is refused with `_UnsafeImagePath` because an attribute-only handle can't pin it; audit finding 5) and no `FILE_SHARE_DELETE`, so nobody can rename the folder or swap in a junction while it is held (verified 2026-10: rename fails with a sharing violation; a handle with only `FILE_READ_ATTRIBUTES` does *not* block it, because Windows ignores the share mode of attribute-only opens). The leaf is opened with `FILE_FLAG_OPEN_REPARSE_POINT` (`_win_open()` always adds it), and any reparse point, on a folder or the leaf, is refused (this includes OneDrive placeholders if Windows exposes their reparse attribute). Pinned folders can't be renamed by other programs during a run either.
- **Permissions and output handles**: `_image_edit()` captures mode from `fstat()` on the opened source and keeps the exclusively created temporary descriptor through all writes (`_temp_file_object()` closes, and on Windows discards, the descriptor even if wrapping it fails). Before the first byte is written it refuses an EFS-encrypted source (`_efs_encrypted()`: `FILE_ATTRIBUTE_ENCRYPTED`) whose temporary isn't encrypted: a temporary created in an encrypted folder is encrypted at creation and allowed, one in a plain folder would replace the image with a plaintext copy readable without the EFS key (audit finding 6; recipients beyond the folder's are not compared). Writers use its file object (including Pillow saves and pyexiv2 reads/writes), then apply source mode through the descriptor. Linux extended attributes are captured from the source descriptor and restored on the output, avoiding an ACL-mask-to-group-permission escalation; only `_kept_xattr()` names count (review finding 3): `ACL_XATTR` (`system.posix_acl_access`; a read failure other than `ENODATA` propagates, and inherited default-ACL entries on the temporary are removed, fail closed), `user.*` (unreadable ones skipped), and `SELINUX_XATTR` (`security.selinux`, best effort: setting it needs a relabel permission the user may lack, e.g. for an image moved in from `/tmp`, so a failure only logs at debug and the temporary keeps its folder's default label; it is never removed). Other `security.*`/`trusted.*` attributes (`security.capability`, `security.ima`) can't be written unprivileged and are dropped, which only narrows access. `_restore_xattrs()` does the restore. On POSIX `_restore_group()` first gives the temporary the source's owning group (`fchown`), so the kept mode doesn't grant group bits to the temporary's group (primary or setgid-directory group; security review finding 4); if `fchown` fails for any reason (`EPERM` when this user isn't a member, `EINVAL` for a gid unmapped in a container/user namespace, `EOPNOTSUPP`/`ENOSYS` on some NFS/FUSE mounts), group permission bits are dropped instead and `_warn()` says so, and the other bits are limited to the owning group's former rights (`(mode & ~0o077) | (mode & 0o007 & _owning_group_bits(...))`): source-group members now count as others, so plain `mode & ~0o070` would give them the other-read of a `0604` file (security audit finding 7). With a POSIX ACL the mode's group bits are the ACL mask, not the group's rights (`group::---` with `mask::rw-` shows as `0664`), so `_owning_group_bits()` reads the `ACL_GROUP_OBJ` entry from the captured `system.posix_acl_access` value instead (an ACL without one counts as no access; PR #29 Greptile review). Narrower, never broader. Permissions are captured only for edits (`_source_bytes(..., permissions=True)`); plain reads skip them. On Windows `_file_attributes()` instead captures the source's security descriptor (`GetSecurityInfo`, DACL only, key `_Win.SECURITY_KEY`) when the volume has `FILE_PERSISTENT_ACLS` (not FAT32/exFAT, which skip all DACL handling), and the temporary is created with it via `SECURITY_ATTRIBUTES` and share mode 0, so it is never readable under the folder's broader inherited permissions and no other process can hold a handle to it. `CreateFileW` copies the entries verbatim (inherited `ID` entries included) but drops the DACL's `AI` auto-inherited control flag; `_create_windows_temp()` compares DACL entries plus the protected flag (`_windows_dacl()`) and fails closed on any other difference. `SetSecurityInfo` is deliberately not used: with unprotected DACLs it recomputes inherited entries from the folder, which would make files with stale inherited entries fail. The owner becomes the current user (no privilege to keep the original). `_apply_permissions()` then only sets the mode (read-only attribute) on Windows. No `copy2`/`copymode` or temporary pathname reopening. Source timestamps are not copied.
- **Commit**: `_image_edit()` checks the temporary's identity and that the source is still the same, unmodified file (`_same_version()`: identity, size, `st_mtime_ns`, so an edit by another program during the write isn't overwritten) and uses descriptor-relative replacement/cleanup on POSIX. Its safety against other users relies on the directory ownership/write restrictions, not on an atomic check-and-rename. Windows renames the still-open temporary through its handle (`_rename_windows_handle()`: `SetFileInformationByHandle` with `FileRenameInfoEx`, flags replace-if-exists + POSIX semantics + ignore-read-only, NTFS on Windows 10 1809+; falls back to plain `FileRenameInfo` on `ERROR_INVALID_FUNCTION`/`NOT_SUPPORTED`/`INVALID_PARAMETER`), inside pinned folders, so no other file can take the temporary's place and the target name can't be redirected. Read-only images are replaced and stay read-only on NTFS. Windows has no equivalent of the POSIX "folder not writable by others" check: someone who may write the folder can still swap the leaf between the identity check and the rename, which only replaces that name inside the same pinned folder. Tested on local NTFS only (Windows 11, 2026-10); **FAT32/exFAT and network shares (SMB) are untested** (see Known Limitations).
- **`robust_replace(src, dst)`**: Retries replacement (`Path.replace`, descriptor-relative `os.replace` with `parent_fd`, or the Windows handle rename with `source_fd`) up to 10× with 0.5s delay between attempts (none after the last) upon `OSError` across **all platforms** (handles Windows file lock release and transient I/O locks). The final `OSError` (`Failed to replace <dst> with <src> …`) names the last underlying error and chains it (`from`).
- **Temp cleanup**: `_image_edit()` wraps cleanup in `finally` with directory-relative `unlink` on POSIX. On Windows a failed edit discards the temporary through its handle before closing it (`_discard_windows_temp()`: clear read-only via the descriptor, then `FileDispositionInfo` delete-on-close), so even a temporary already made read-only is removed. It first checks that the handle still sits at the temporary's name: after a completed handle rename (e.g. Ctrl+C right after it) the handle *is* the committed image and must not be deleted. `_rename_windows_handle()` sizes the name in UTF-16 code units (non-BMP characters take two), copies it as raw bytes (a `c_char` array would stop at the first NUL) and refuses relative targets (`FileRenameInfo` resolves those against the current directory).

## GIF Processing
- Tagging and clearing never decode a GIF: `_set_gif_comment()` walks its blocks (header, logical screen descriptor and global color table, then `21` extensions with their data sub-blocks, `2C` images with descriptor, local color table, LZW code size and sub-blocks), drops every comment extension (`21 FE`) and, when tagging, writes one new UTF-8 comment (sub-blocks of ≤255 bytes) right after the global header, where Pillow reads it as `info["comment"]`. Every other byte is copied, so frames, palettes, disposal methods, transparency, durations, the loop count (or its absence) and application extensions stay exactly as they were, in memory proportional to the file (review finding 2, audit finding 11; Pillow's re-encode used to drop `disposal=2` and smear transparent animations).
- A `GIF87a` header becomes `GIF89a` only when a comment is written (comment extensions are a GIF89a feature). A GIF that ends at a block boundary without its `3B` trailer gets one; bytes after the trailer, or an unknown block byte after the last image, are kept verbatim; a GIF that ends inside a block raises `ValueError("Truncated GIF file")` and is left unchanged.

## Animated GIF & WebP
README's known issue: the model only sees the first frame. `_model_image()` now sends only the first frame explicitly; with `--max-pixels 0` the whole file is sent and the servers decode only its first frame anyway (manual runs in 2026-10 confirmed that for animated GIFs on both backends: a white first frame was tagged `blank`, `white`).
- Normal WebP tagging/clearing goes through pyexiv2, which edits metadata in place: frames, per-frame durations and loop count survive.
- Auto-heal keeps the animation too: `_sanitize_with_pillow()` re-saves animated images (WebP, APNG) with `save_all=True` plus per-frame durations and loop. It decodes every frame and Pillow's writers keep them all, so it first refuses animations over `MAX_ANIMATION_PIXELS` (frames × width × height, 250 M) with `Animation too large to repair` (audit finding 11).

## Non-standard PNG chunks
- pyexiv2 edits PNGs in place, so other text chunks (`tEXt`/`zTXt`/`iTXt`), `pHYs` (DPI) and private ancillary chunks survive tagging and clearing. Tagging adds an `eXIf` chunk and an `iTXt` `XML:com.adobe.xmp` chunk; clearing removes both. Exiv2 rewrites a `tEXt` `Description` (its PNG comment) as `iTXt`, keeping the text.
- The Pillow auto-heal re-save passes no `pnginfo`/`dpi`, so on that path other text chunks and DPI are lost.

## Metadata Auto-Healing & Sanitization
If `pyexiv2` raises a `RuntimeError` whose message contains `IFD` or `corrupt` (case-insensitive):
1. Re-save the original into the temp file with Pillow via `_sanitize_with_pillow()` (`quality=95`) to strip broken headers. Animated WebP/APNG keep all frames, durations and loop. The format is the detected one.
2. Tagging (`write_metadata()`): retry the pyexiv2 write once on the sanitized file; a second failure propagates (`FAILED`). Clearing (`_clear_standard()`): no retry, the Pillow re-save *is* the clear (Pillow writes no EXIF/XMP/IPTC by default).

*Caution*: the re-save re-encodes JPEG/WebP (no `lossless=True`, so lossless WebP becomes lossy) and keeps only pixels and animation: EXIF (incl. Orientation, so photos may show rotated), XMP, IPTC, DPI and, for JPEG/WebP, the ICC profile are dropped.

## Known Limitations & Maintenance Notes
- **Tests**: `python3 -m pytest` covers parsing, metadata round-trips for every format, non-ASCII file and folder names, mislabeled extensions, GIF block editing (byte-for-byte preservation, disposal/transparency, extensions, truncation), auto-healing (simulated), temp-file cleanup, fake-backend pipeline, quit listener (Windows `msvcrt` path via a fake `msvcrt`), Windows file safety (folder pins, junctions, DACLs, read-only images, rename fallback; `windows_only` in `test_file_safety.py`) and CLI. An autouse fixture in `conftest.py` sets `umask 0o022`, so folders the tests create pass `_check_directory()` under umask 0002/0000; `other_group_or_skip()` only returns a secondary group a probe file can really be `chown`ed to (unmapped groups in containers show up as the overflow gid and fail with `EINVAL`). CI runs them on Linux (3.13–3.14) and Windows (3.14). `test_cli.py::test_unreachable_server_stops_before_any_image` takes ~10s (the server check timeout) under WSL2 mirrored networking, where a connect to a closed localhost port isn't refused; not a code bug. Tagging *quality* still needs a manual run with `--run-integration` against real images.
- **Known bugs**: none currently pinned. When adding one, pin it as a strict `xfail` (fixing it makes it XPASS → remove the marker).
- **Windows FAT32/exFAT and network shares untested**: the Windows file safety (DACL copy that fails closed if the result differs, handle rename via `FileRenameInfoEx` with a `FileRenameInfo` fallback, folder pins) was only exercised on local NTFS. FAT32/exFAT have no DACLs (skipped via `FILE_PERSISTENT_ACLS`, untested on a real drive) and no POSIX-semantics rename; SMB shares may report security or rename support differently, and a server that rewrites DACLs on create (e.g. Samba without `vfs_acl_xattr`) would make the fail-closed check reject every image there (deliberate: no semantic DACL comparison). If any of that misbehaves, every image on such a drive fails although the old pathname code tagged them. Before relying on it (or before merging changes here), try a tag and a `--clear` run on a USB stick and a network folder. Read-only images on non-NTFS drives may still fail to be replaced.
- **Untested dependency minimums (future work)**: CI tests Python 3.13–3.14, but only against the versions in `requirements-dev.lock`. The `>=` lower bounds in `requirements.txt` were never tested as minimums. Known and accepted for now.
- **No macOS CI**: CI runs on Linux and Windows only. The `msvcrt` quit listener is covered with a fake `msvcrt`; a real console `Q` press is still untested.
- **SonarQube accepted issue**: `pythonsecurity:S8707` path traversal on `--log` (now reported in `_open_log()`, earlier in `setup_logging()`) is mitigated by `_log_path_error()` (see Logging), which Sonar doesn't recognize as a sanitizer; it stays Accepted. Its suggested fix (confine to the current directory) was rejected because it breaks absolute log paths.
- **SonarQube false positives** (dismissed in Sonar; don't "fix" them in code): regex-backtracking warnings on `parse_model_output()` patterns (measured linear on 200k-char adversarial inputs); `python:S9152` "cleanup after yield may be skipped" in `_image_edit()` (the code after `yield` is the commit, which must not run when the `with` body raises; the cleanup is in its `except BaseException`/`finally`).
