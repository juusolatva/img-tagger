# AGENTS.md

This file provides guidance to agents when working with code in this repository.

## Project Overview
- `img_tagger.py` — single-file CLI: tags JPEG/WebP/PNG/GIF files via a vision-language model on a local or LAN server (Ollama or LM Studio), writing tags into image metadata. `--clear` strips tags/metadata back out instead (used to reset images for testing; no model backend needed).
- `prompt.txt` — externalized LLM prompt; takes precedence over the `DEFAULT_PROMPT` fallback hardcoded in `img_tagger.py`.
- Flat repo layout: no package structure, not installable (`pyproject.toml` only holds Ruff and coverage config; no `setup.py`). Tests live in `tests/` (pytest, configured by `pytest.ini`). CI: GitHub Actions (see CI section).
- `.serena/` (tracked): Serena project config and memories (`core`, `conventions`, `suggested_commands`, `task_completion`, `tech_stack`, `memory_maintenance`) that condense this file. When a fact here changes, update the matching memory in the same change.
- **Git workflow**: commits are allowed; prefer working on a branch and opening a pull request rather than pushing directly to `main`.
- Requires **Python 3.13+**.

## Build/Lint/Test Commands
Ruff (lint + format) is configured in `pyproject.toml`; CI fails on any Ruff finding or unformatted file. SonarQube Cloud (project `juusolatva_img_tagger`) runs in CI; keep functions under its cognitive-complexity limit of 15 by extracting `_private` helpers.
- Dependencies: `pip install -r requirements.txt` (or `pip3 install -r requirements.txt`); dev deps (pytest, pytest-cov, Ruff): `pip install -r requirements-dev.txt`
- Lint/format: `ruff check .` and `ruff format .` (CI runs `ruff format --check`). Use the Ruff version pinned in `requirements-dev.txt`.
- Run tests: `python3 -m pytest` (offline: images generated on the fly, model backends faked). With coverage like CI: `python3 -m pytest --cov`
- Integration tests (opt-in, need a live backend + images in git-ignored `test_images/`; copies images to a temp dir, prints tags for manual quality review): `python3 -m pytest -m integration --run-integration -s [--tagger-backend lm-studio] [--tagger-host URL] [--tagger-model M] [--images-dir DIR]`. `--tagger-model` defaults to Ollama's `qwen3-vl:8b`, so with LM Studio also pass its model id. The `client` fixture uses `_create_client()`, so runs get `DEFAULT_TIMEOUT` and LM Studio's `max_retries=0`.
- Run tagger (Ollama, default): `python3 img_tagger.py <directory>`
- Run tagger (LM Studio): `python3 img_tagger.py <directory> --backend lm-studio --model qwen/qwen3-vl-8b` (LM Studio's own model id; see Backends)
- Recursive, custom model/workers: `python3 img_tagger.py <directory> -r --model <model> --workers 4`
- Clear all tags: `python3 img_tagger.py <directory> --clear [-r] [--workers N]`
- Help: `python3 img_tagger.py -h`
- Request timeout (seconds, default 600): `python3 img_tagger.py <directory> --timeout 1200`
- Logging: `python3 img_tagger.py <dir> --log output.log` (see Logging under Core Rules)
- Note: commands use `python3` (Linux/macOS); on Windows use `python` (`python3` there is often the Microsoft Store alias).

## CI
`.github/workflows/ci.yml` (GitHub Actions) runs on pushes to `main`, pull requests and manual dispatch:
- **Ruff**: `ruff check` and `ruff format --check --diff`. `ruff-action` reads the Ruff version from the `ruff==` pin in `requirements-dev.txt`.
- **Tests**: `pytest --cov --cov-report=xml` on Ubuntu with Python 3.13 and 3.14, plus `windows-latest` with 3.14 (`fail-fast: false`; job names `Tests (<os>, Python <version>)`). Integration tests are skipped (no backend). Installs from `requirements-dev.lock` with `--require-hashes --only-binary :all:`, so every locked package needs a wheel for every matrix version and OS (Linux and Windows). The 3.14 jobs upload `coverage.xml` as the artifacts `coverage` (Linux) and `coverage-windows`; Sonar reads both (`sonar.python.coverage.reportPaths`), so the Windows-only file-safety branches count as covered.
- **SonarQube Cloud**: runs after the tests and scans with the downloaded `coverage.xml`. Settings are in `sonar-project.properties` (sources `.`, `tests/**` excluded and treated as tests, `sonar.python.version` 3.13–3.14). Needs `SONAR_TOKEN` as both an Actions secret and a Dependabot secret (Dependabot-triggered runs read only Dependabot secrets). `if:` can't read secrets, so the job maps it to a job-level env var and the scan step runs only when that is non-empty; otherwise a warning annotation explains the skip. Fork PRs get no secrets, hence no scan and no SonarQube quality-gate status: don't make that status a required check. Coverage is configured in `[tool.coverage.run]` in `pyproject.toml` (branch coverage, `tests/` omitted, `relative_files = true` so Sonar can map the paths in `coverage.xml` to its sources, `patch = ["subprocess"]` so the `test_cli.py` subprocess runs count toward `setup_logging()` and the end-to-end paths). With that patch, tqdm's multiprocessing lock starts a `resource_tracker` child that outlives pytest-cov's combine and leaves an empty `.coverage.<host>.pid…` file (git-ignored, harmless).
- Every job in `ci.yml` has a `timeout-minutes`, and checkouts use `persist-credentials: false` (no job pushes).
- **OSV-Scanner** (`.github/workflows/osv-scanner.yml`): calls `google/osv-scanner-action`'s reusable workflows — full scan (`osv-scanner-reusable.yml`) on pushes to `main`, weekly schedule and manual dispatch, and PR diff scan (`osv-scanner-reusable-pr.yml`) on pull requests and `merge_group` (with `upload-sarif` disabled on fork PRs, which lack `security-events: write`). Both pass `--lockfile=requirements.txt:requirements-dev.lock`, `--no-resolve` and `-r ./` so the `.lock` file is scanned as a pip requirements lockfile and `requirements*.txt` minimum bounds are checked without resolving transitive dependencies from PyPI.
- Third-party actions are pinned to commit SHAs with a `# vX.Y.Z` comment. GitHub's own `actions/*` use major-version tags.
- **Dependabot** (`.github/dependabot.yml` holds schedule, grouping and cooldown): updates GitHub Actions, SHA pins together with their `# vX.Y.Z` comment. Its pip entry only ignores every package, which also blocks security-update PRs: Dependabot's pip updater reads only `*.txt`/`*.in` files, so it would bump the bounds in `requirements*.txt` and never regenerate `requirements-dev.lock`. Bump Python packages by hand (below).
- **`requirements-dev.lock`**: hash-locked, cross-platform lock of `requirements-dev.txt` (and thus `requirements.txt`) for Python ≥3.13. Only CI installs it; end users still get the `>=` bounds. After changing either requirements file, regenerate it with `uv pip compile requirements-dev.txt --universal --python-version 3.13 --generate-hashes --no-header -o requirements-dev.lock`. That keeps the existing pins where they still fit; to bump versions add `--upgrade` (all) or `-P <package>` (one).
- Changing the supported Python range means updating the CI matrix, `sonar.python.version`, Ruff `target-version`, the lock's `--python-version` and the static Python badge in `README.md` together.

## Backends
- `--backend ollama` (default): `ollama` Python client, default host `http://localhost:11434`. `get_tags_ollama()` passes guarded image *bytes* in `images`; the client base64-encodes the snapshot without reopening its path, so a remote Ollama needs no shared filesystem.
- `--backend lm-studio`: `openai` client against LM Studio's OpenAI-compatible API, default host `http://localhost:1234`. `get_tags_lm_studio()` sends the file as a base64 data URL whose MIME type comes from the Pillow-detected format (fallback `image/jpeg`), not the extension. `api_key="lm-studio"` is a required placeholder string, not a real credential.
- **What the model gets**: the original file, whole and unmodified (no resizing, no frame extraction), so for animated GIF/WebP/APNG the server decodes only the first frame (see Animated GIF & WebP).
- **`--model`**: one default for both backends, `qwen3-vl:8b`, which is Ollama naming. LM Studio ids differ (e.g. `qwen/qwen3-vl-8b`; list them at `<host>/v1/models`), so with LM Studio `--model` must always be passed.
- **LM Studio vision setup** (found by testing, not visible in code): a GGUF model only counts as vision-capable (`type: "vlm"` in `<host>/api/v0/models`) once its vision projector `mmproj-*.gguf` is downloaded; otherwise every image fails with HTTP 400 `... does not support image inputs`. LM Studio loads the model on the first request, so the first image is slower.
- **`--host`**: no argparse default; `process_directory(host=None)` fills in the backend's localhost URL from `DEFAULT_HOSTS` (also for imported callers), so the ollama client never falls back to `OLLAMA_HOST`. The ollama client normalizes hosts (`192.168.1.10` → `http://192.168.1.10:11434`); LM Studio uses `f"{host}/v1"` verbatim, so pass `http://host:port` without `/v1`. Servers on another LAN machine work.
- **Request timeout**: `--timeout` (default `DEFAULT_TIMEOUT` = 600s, must be > 0; `nan` is rejected explicitly with `math.isnan()` because `nan <= 0` is false) is passed to both clients by `_create_client()`. It must cover the whole non-streamed reply, including model loading. A timeout raises in the worker and marks that image `FAILED`. The LM Studio client uses `max_retries=0`: the openai default (2) would resend a timed-out request to a server still busy with it.

## Core Rules & Architecture
- **CLI**: `main(argv=None) -> int` parses (`_build_parser()`), validates (`_log_path_error()`, then `_argument_error()`; invalid → print `Error: …`, return 1) and calls `process_directory()`; `__main__` is only `sys.exit(main())`. Argument handling is tested in-process (`TestMain` in `test_cli.py`); subprocess tests cover logging and console encoding. Defaults live in `DEFAULT_MODEL`, `DEFAULT_HOSTS` and `DEFAULT_TIMEOUT`.
- **Pipeline**: `process_directory()` → `_find_images()` (extension filter `IMAGE_EXTENSIONS`, `iterdir()`/`rglob("*")`) → `_load_prompt()` → `_create_client()` → quit listener → `_run_tasks()` (`ThreadPoolExecutor` + `as_completed` + tqdm; each `process_single_image()` result `(status, name, message, duration)` goes to `_RunStats.record()`) → `_print_report()`. Per image: `get_image_format()` (Pillow verify; invalid → `FAILED`; a format outside `TAGGABLE_FORMATS`, e.g. BMP or MPO, → `FAILED` before any model call) → `is_already_processed()` (`SKIPPED`) → stop check (`CANCELLED`) → backend call → `parse_model_output()` → `tag_image()`.
- **Format dispatch**: `tag_image()`, `is_already_processed()` and `clear_tags()` all route on the Pillow-detected format, not the extension (a PNG named `.gif` is tagged, detected and cleared via pyexiv2). The extension decides only when Pillow can't read the file (`_is_gif()`).
- **Worker limit**: Max 4 concurrent workers (matches both backends' default concurrency limits). Default is 1. Enforced in CLI argument validation (`_argument_error()`: `1 <= workers <= 4`), not inside `process_directory()` itself.
- **Skip marker**: Files with `[PROCESSED BY AI]` are skipped automatically (`is_already_processed()`). JPEG/WebP/PNG: any EXIF or XMP value (`_pyexiv2_has_marker()`); if pyexiv2 finds none or fails, any string in Pillow's `img.info` (`_pillow_has_marker()`, e.g. PNG text chunks). GIF: the comment only. Unreadable metadata → `_warn()` and treated as not tagged.
- **Prompt source**: `prompt.txt` in the script directory takes precedence over the in-code `DEFAULT_PROMPT` fallback. If `prompt.txt` exists but cannot be read, execution aborts (`sys.exit(1)`).
- **Tag count & normalization**: Output is normalized via `normalize_tags()` (strip whitespace, lowercase, order-preserving deduplication, capped at 12 tags). Nothing else is rewritten or filtered: underscores stay (Qwen sometimes replies `digital_art`), and so do non-English tags (Qwen models occasionally emit a Chinese tag despite the English-only prompt). Deliberately unfiltered: `prompt.txt` may ask for tags in any language. Fewer than 6 valid tags after parsing marks that image as `FAILED`.
- **Tag parsing**: `parse_model_output()` first drops everything up to the last `</think>` (reasoning from thinking models), then tries several patterns in order:
  1. JSON array (`json.loads` on full string or bracketed `[...]` substring).
  2. Bullet points at line start (`[-•★●]`, minimum 6 items expected; splits each line on commas). Hyphens inside tags (`tag-1`) are not bullets.
  3. Numbered lists (`\d+\.`, minimum 6 items expected; splits each line on commas).
  4. Intro text: `tags`/`keywords` within the first ~40 chars, followed by a colon later on the same line (`Here are the tags for this image:`) or a dash right after (`Keywords -`). Parsed via `parse_text_tags()`, which drops common English stop words but keeps short tags like `3d`/`ui`.
  5. Comma- and/or newline-separated list fallback.

  Only the JSON pattern falls through when it yields fewer than 6 tags; a matched bullet/numbered/intro pattern returns its result (or `None` → `FAILED`) without trying later patterns.
- **Concurrency & Locks**: Images are processed in parallel via `ThreadPoolExecutor`. `pyexiv2` is not thread-safe: all `pyexiv2` reads (`_pyexiv2_has_marker()`), writes (`write_metadata()`) and clears (`_clear_standard()`) are serialized through `metadata_lock = threading.Lock()`. In `write_metadata()` the lock also covers the auto-heal re-save; `_clear_standard()` holds it only around pyexiv2. Replacement occurs after releasing the metadata lock. Model API calls and other Pillow operations (GIF read/write, format verification, the skip-check fallback) are intentionally outside the lock to preserve concurrency.
- **Logging**: The `img_tagger` logger has a `NullHandler`, so without `--log` nothing is logged (no stray stderr warnings or tracebacks over the progress bar). The console shows results via `tqdm.write()`/`print()`. Problems the user must see either way go through `_warn()`, which both logs a warning and prints `  Warning: …` via `tqdm.write()`. These are pyexiv2/Pillow metadata read failures in `is_already_processed()` and the auto-heal re-save in `write_metadata()`. `--log` (`setup_logging()`) appends to the file with our logger at `DEBUG` and other libraries at `INFO`, which keeps httpx request lines and drops Pillow's per-chunk noise. The log records run settings, the prompt, each image's outcome and duration, raw model replies, tracebacks and a final summary. Because raw replies can be steered by text inside an image, `main()` first checks the path with `_log_path_error()`: it must end in `.log` (case-insensitive) and, if it exists, be a regular file and not a symlink; otherwise exit 1 before anything is created. This keeps a misused `--log` (e.g. a prompt-injected agent) from appending to shell profiles, keys or source files. The path is deliberately not confined to the current directory (`--log /tmp/run.log` stays valid). `_log_path_error()` is only the early, friendly check: `setup_logging()` then opens the file exactly once with `_open_log()` (POSIX `O_NOFOLLOW | O_APPEND | O_CREAT | O_NONBLOCK`, Windows `CreateFileW` with `FILE_APPEND_DATA` and `FILE_FLAG_OPEN_REPARSE_POINT`), requires a regular file and, on POSIX, one owned by the current user (a file planted in `/tmp` by someone else is refused), and logs to that stream through a `StreamHandler`. So swapping the leaf for a symlink after the check can't redirect the appends (security review finding 2). An open failure makes `main()` print `Error: Could not open the log file …` and return 1. Ancestor folders are resolved normally (macOS `/tmp` is a symlink).
- **Console encoding**: `main()` reconfigures `sys.stdout` with `errors="replace"`. Redirected output on Windows uses the ANSI code page (e.g. cp1252), which can't encode the `[✓]` success prefix or many file names; without this every success was counted as a failure and a non-ASCII name aborted the run. Tests that call functions directly don't get it (`test_cli.py` covers it via a subprocess with `PYTHONIOENCODING=ascii`).
- **Graceful quit**: Press `Q` during execution to trigger graceful shutdown. Monitored by a daemon thread (`listen_for_quit()`): `_wait_for_quit_windows()` (`msvcrt`) on Windows; on POSIX `_cbreak_stdin()` + `_wait_for_quit_posix()` (`termios`/`tty`/`select`, EOF detection; plain reads with `idle_sleep=0.1` when stdin isn't a tty). The POSIX loop reads the raw fd with `os.read()`, not `sys.stdin.read()`, so Python's buffer can't hide pending keys from `select()`. In-flight requests finish (or hit `--timeout`). Queued tasks still run the format and skip checks, then return `CANCELLED`, which is neither printed nor counted. `process_directory()` sets `stop_event` in its `finally` after every run, so the listener exits (restoring the POSIX terminal) instead of being waited out by `join(timeout=2)`.

## Metadata Schema
- **JPEG / WebP / PNG**:
  - EXIF: `Exif.Photo.UserComment` contains `"<tag1>, <tag2>, ... [PROCESSED BY AI]"`.
  - XMP: `Xmp.dc.subject` contains the raw tag list (`['tag1', 'tag2', ...]`); `Xmp.dc.description` contains `"Tags: <tag1>, <tag2>, ... | [PROCESSED BY AI]"`.
  - Only these three fields are replaced; other EXIF/XMP/IPTC survives tagging (unless auto-heal runs).
- **GIF**: Comment field only (no EXIF/XMP support). Stored as `"<tag1>, <tag2>, ... [PROCESSED BY AI]"`, replacing any existing comment.
- **Metadata Clearing (`--clear`)**: `process_directory(clear=True)` delegates to `clear_directory()` → `clear_tags()` per file (`_clear_standard()` / `_clear_gif()`); no prompt/client/quit listener/report. Per-file failures are printed and logged, not raised. Strips EXIF, XMP, and IPTC (`_clear_all()`) for standard images, and empties `comment=""` for GIFs (every GIF is re-encoded, tagged or not). XMP needs `clear_xmp()` *and* `modify_raw_xmp("")`: on WebP, `clear_xmp()` alone leaves the XMP chunk in the saved file. `clear_comment()` is never called, so JPEG `COM` and PNG `Description` comments survive.

## File Replacement & Atomic Safety
- **Temp file placement**: Temporary files MUST always be created in the target image's directory (POSIX exclusive `os.open(..., dir_fd=parent_fd)`; Windows `_create_windows_temp()`, `CreateFileW` with `CREATE_NEW`). Both use random `tmp<hex>.tmp` names. This ensures replacements remain atomic on the same filesystem/mount point without cross-device link errors.
- **pyexiv2 never gets a path**: `_modify_with_pyexiv2()` reads the retained temporary file object into `pyexiv2.ImageData`, applies the edit and writes `get_bytes()` back with Python; `_pyexiv2_has_marker()` reads via `ImageData` too. On Windows pyexiv2 can't open paths with non-ASCII characters in the file name *or any folder* (`encoding="utf-8"` fails; `"mbcs"` covers only the ANSI code page), and the temp file sits in the image's folder. Never pass a path to `pyexiv2.Image`. (`ImageData` holds the whole file in memory and refuses files ≥2 GB.)
- **Source reads**: `_read_image_bytes()` uses `_image_parent()` and `_source_bytes()`; all Pillow reads use private byte snapshots, and both backends receive guarded bytes. Direct backend/writer entry points use these helpers too. Discovery excludes leaf symlinks; read-time checks also reject symlinked ancestors and nonregular inputs. POSIX opens parents/leaf with `O_NOFOLLOW` and pins directory descriptors. The final image directory must belong to root or the current UID and may not be group/other writable. Ancestors are pinned, not trusted by their reported owner; this avoids trusting unmapped/overflow UIDs in user namespaces. Same-UID/root mutation is outside this boundary. Paths containing `..` are refused. Windows (`parent_fd` is `None` there) pins every ancestor with `_pin_windows_directory()`: a `CreateFileW` handle with `FILE_TRAVERSE` (else `FILE_LIST_DIRECTORY`; a folder granting neither, reached via the bypass-traverse privilege, is only reparse-checked, not pinned) and no `FILE_SHARE_DELETE`, so nobody can rename the folder or swap in a junction while it is held (verified 2026-10: rename fails with a sharing violation; a handle with only `FILE_READ_ATTRIBUTES` does *not* block it, because Windows ignores the share mode of attribute-only opens). The leaf is opened with `FILE_FLAG_OPEN_REPARSE_POINT` (`_win_open()` always adds it), and any reparse point, on a folder or the leaf, is refused (this includes OneDrive placeholders if Windows exposes their reparse attribute). Pinned folders can't be renamed by other programs during a run either.
- **Permissions and output handles**: `_image_edit()` captures mode from `fstat()` on the opened source and keeps the exclusively created temporary descriptor through all writes. Writers use its file object (including Pillow saves and pyexiv2 reads/writes), then apply source mode through the descriptor. Linux extended attributes/ACLs are captured from the source descriptor and restored on the output (inherited extras removed), avoiding an ACL-mask-to-group-permission escalation. On POSIX `_restore_group()` first gives the temporary the source's owning group (`fchown`), so the kept mode doesn't grant group bits to the temporary's group (primary or setgid-directory group; security review finding 4); if this user isn't a member of that group, group permission bits are dropped instead and `_warn()` says so (narrower, never broader). Permissions are captured only for edits (`_source_bytes(..., permissions=True)`); plain reads skip them. On Windows `_file_attributes()` instead captures the source's security descriptor (`GetSecurityInfo`, DACL only, key `_Win.SECURITY_KEY`) when the volume has `FILE_PERSISTENT_ACLS` (not FAT32/exFAT, which skip all DACL handling), and the temporary is created with it via `SECURITY_ATTRIBUTES` and share mode 0, so it is never readable under the folder's broader inherited permissions and no other process can hold a handle to it. `CreateFileW` copies the entries verbatim (inherited `ID` entries included) but drops the DACL's `AI` auto-inherited control flag; `_create_windows_temp()` compares DACL entries plus the protected flag (`_windows_dacl()`) and fails closed on any other difference. `SetSecurityInfo` is deliberately not used: with unprotected DACLs it recomputes inherited entries from the folder, which would make files with stale inherited entries fail. The owner becomes the current user (no privilege to keep the original). `_apply_permissions()` then only sets the mode (read-only attribute) on Windows. No `copy2`/`copymode` or temporary pathname reopening. Source timestamps are not copied.
- **Commit**: `_image_edit()` checks source/temporary inode identities and uses descriptor-relative replacement/cleanup on POSIX. Its safety against other users relies on the directory ownership/write restrictions, not on an atomic check-and-rename. Windows renames the still-open temporary through its handle (`_rename_windows_handle()`: `SetFileInformationByHandle` with `FileRenameInfoEx`, flags replace-if-exists + POSIX semantics + ignore-read-only, NTFS on Windows 10 1809+; falls back to plain `FileRenameInfo` on `ERROR_INVALID_FUNCTION`/`NOT_SUPPORTED`/`INVALID_PARAMETER`), inside pinned folders, so no other file can take the temporary's place and the target name can't be redirected. Read-only images are replaced and stay read-only on NTFS. Windows has no equivalent of the POSIX "folder not writable by others" check: someone who may write the folder can still swap the leaf between the identity check and the rename, which only replaces that name inside the same pinned folder. Tested on local NTFS only (Windows 11, 2026-10); **FAT32/exFAT and network shares (SMB) are untested** (see Known Limitations).
- **`robust_replace(src, dst)`**: Retries replacement (`Path.replace`, descriptor-relative `os.replace` with `parent_fd`, or the Windows handle rename with `source_fd`) up to 10× with 0.5s delay upon `OSError` across **all platforms** (handles Windows file lock release and transient I/O locks).
- **Temp cleanup**: `_image_edit()` wraps cleanup in `finally` with directory-relative `unlink` on POSIX. On Windows a failed edit discards the temporary through its handle before closing it (`_discard_windows_temp()`: clear read-only via the descriptor, then `FileDispositionInfo` delete-on-close), so even a temporary already made read-only is removed. It first checks that the handle still sits at the temporary's name: after a completed handle rename (e.g. Ctrl+C right after it) the handle *is* the committed image and must not be deleted. `_rename_windows_handle()` sizes the name in UTF-16 code units (non-BMP characters take two), copies it as raw bytes (a `c_char` array would stop at the first NUL) and refuses relative targets (`FileRenameInfo` resolves those against the current directory).

## GIF Processing
- Frames reach `Image.save()` through a generator (`append_images=frame_generator()`), but this does not bound memory: Pillow's GIF writer collects every frame before writing, so peak memory grows with frame count × frame size.
- Per-frame durations are extracted from `img.info` and preserved (defaulting to 100ms if missing). Pillow merges identical consecutive frames on save (durations summed), so the frame count can drop; tests use all-different frames for this reason (`make_gif()`).
- The loop count is kept only if the source has one (`_gif_loop_kwargs()`): a GIF without it plays once, and saving with `loop=0` would make it loop forever.
- GIF tagging and clearing re-encode the whole file through Pillow, so anything Pillow doesn't round-trip is lost: e.g. custom application extensions (`21 FF` blocks other than looping) are dropped.

## Animated GIF & WebP
README's known issue: the model only sees the first frame. Neither backend extracts frames (see Backends); manual runs in 2026-10 confirmed it for animated GIFs on both backends (a white first frame was tagged `blank`, `white`). Animated WebP takes the same path, untested.
- Normal WebP tagging/clearing goes through pyexiv2, which edits metadata in place: frames, per-frame durations and loop count survive.
- Auto-heal keeps the animation too: `_sanitize_with_pillow()` re-saves animated images (WebP, APNG) with `save_all=True` plus per-frame durations and loop.

## Non-standard PNG chunks
- pyexiv2 edits PNGs in place, so other text chunks (`tEXt`/`zTXt`/`iTXt`), `pHYs` (DPI) and private ancillary chunks survive tagging and clearing. Tagging adds an `eXIf` chunk and an `iTXt` `XML:com.adobe.xmp` chunk; clearing removes both. Exiv2 rewrites a `tEXt` `Description` (its PNG comment) as `iTXt`, keeping the text.
- The Pillow auto-heal re-save passes no `pnginfo`/`dpi`, so on that path other text chunks and DPI are lost.

## Metadata Auto-Healing & Sanitization
If `pyexiv2` raises a `RuntimeError` whose message contains `IFD` or `corrupt` (case-insensitive):
1. Re-save the original into the temp file with Pillow via `_sanitize_with_pillow()` (`quality=95`) to strip broken headers. Animated WebP/APNG keep all frames, durations and loop. The format is the detected one.
2. Tagging (`write_metadata()`): retry the pyexiv2 write once on the sanitized file; a second failure propagates (`FAILED`). Clearing (`_clear_standard()`): no retry, the Pillow re-save *is* the clear (Pillow writes no EXIF/XMP/IPTC by default).

*Caution*: the re-save re-encodes JPEG/WebP (no `lossless=True`, so lossless WebP becomes lossy) and keeps only pixels and animation: EXIF (incl. Orientation, so photos may show rotated), XMP, IPTC, DPI and, for JPEG/WebP, the ICC profile are dropped.

## Known Limitations & Maintenance Notes
- **Tests**: `python3 -m pytest` covers parsing, metadata round-trips for every format, non-ASCII file and folder names, mislabeled extensions, GIF frame/duration/loop preservation, auto-healing (simulated), temp-file cleanup, fake-backend pipeline, quit listener (Windows `msvcrt` path via a fake `msvcrt`), Windows file safety (folder pins, junctions, DACLs, read-only images, rename fallback; `windows_only` in `test_file_safety.py`) and CLI. CI runs them on Linux (3.13–3.14) and Windows (3.14). `test_cli.py::test_failed_image_prints_no_traceback` hangs (60s timeout) under WSL2 mirrored networking, where a connect to a closed localhost port isn't refused; not a code bug. Tagging *quality* still needs a manual run with `--run-integration` against real images.
- **Known bugs**: none currently pinned. When adding one, pin it as a strict `xfail` (fixing it makes it XPASS → remove the marker).
- **Windows FAT32/exFAT and network shares untested**: the Windows file safety (DACL copy that fails closed if the result differs, handle rename via `FileRenameInfoEx` with a `FileRenameInfo` fallback, folder pins) was only exercised on local NTFS. FAT32/exFAT have no DACLs (skipped via `FILE_PERSISTENT_ACLS`, untested on a real drive) and no POSIX-semantics rename; SMB shares may report security or rename support differently, and a server that rewrites DACLs on create (e.g. Samba without `vfs_acl_xattr`) would make the fail-closed check reject every image there (deliberate: no semantic DACL comparison). If any of that misbehaves, every image on such a drive fails although the old pathname code tagged them. Before relying on it (or before merging changes here), try a tag and a `--clear` run on a USB stick and a network folder. Read-only images on non-NTFS drives may still fail to be replaced.
- **Untested dependency minimums (future work)**: CI tests Python 3.13–3.14, but only against the versions in `requirements-dev.lock`. The `>=` lower bounds in `requirements.txt` were never tested as minimums. Known and accepted for now.
- **No macOS CI**: CI runs on Linux and Windows only. The `msvcrt` quit listener is covered with a fake `msvcrt`; a real console `Q` press is still untested.
- **SonarQube accepted issue**: `pythonsecurity:S8707` path traversal on `--log` in `setup_logging()` is mitigated by `_log_path_error()` (see Logging), which Sonar doesn't recognize as a sanitizer; it stays Accepted. Its suggested fix (confine to the current directory) was rejected because it breaks absolute log paths.
- **SonarQube false positives** (dismissed in Sonar; don't "fix" them in code): regex-backtracking warnings on `parse_model_output()` patterns (measured linear on 200k-char adversarial inputs); `python:S9152` "cleanup after yield may be skipped" in `_image_edit()` (the code after `yield` is the commit, which must not run when the `with` body raises; the cleanup is in its `except BaseException`/`finally`).
